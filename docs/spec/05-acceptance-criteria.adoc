[[acceptance]]
= Gherkin-Szenarien beweisen jede Regel

Jedes Szenario trägt die Tags des Use Case und der Regeln, die es beweist.
Jede Extension hat mindestens ein Szenario; die Extension steht im Szenarionamen.
Die Szenarien sind so formuliert, dass sie später unverändert als `.feature`-Dateien laufen können.

== UC-01 Probeprüfung ablegen

# language: de

  Grundlage:
    Angenommen der Fragenbestand enthält 50 Fragen mit aktueller Version "Released" in "de" und "en"

  @UC-01 @BR-20 @BR-21 @BR-22 @BR-24 @BR-25 @BR-27
  Szenario: MSS – Prüfung starten zieht 40 Fragen ohne Lösungen

    Und jede Frage ist eine Released-Version in "de"

    Dann zeigt das System erreichte Punkte, erreichbare Punkte, Prozentwert und "bestanden" oder "nicht bestanden"

  @UC-01 @BR-22
  Szenario: Laufende Prüfung behält ihre Versionen

  @UC-01 @BR-29

== Bewertung

[source,gherkin]
----
# language: de
Funktionalität: Bewertung nach den offiziellen Prüfungsregeln

  @UC-01 @BR-40
  Szenariogrundriss: A-Frage
    Angenommen eine A-Frage mit 2 Punkten und der korrekten Option "B"
    Wenn der Kandidat <Auswahl> wählt
    Dann erhält er <Punkte> Punkte

    Beispiele:
      | Auswahl | Punkte |
      | B       | 2      |
      | C       | 0      |
      | B, C    | 0      |

  @UC-01 @BR-41
  Szenariogrundriss: P-Frage mit 2 korrekten Optionen
    Angenommen eine P-Frage mit 2 Punkten und den korrekten Optionen "A" und "C"
    Wenn der Kandidat <Auswahl> wählt
    Dann erhält er <Punkte> Punkte

    Beispiele:
      | Auswahl  | Punkte |
      | A, C     | 2      |
      | A        | 1      |
      | A, B     | 0      |
      | B        | 0      |
      | A, B, C  | 0      |

  @UC-01 @BR-42
  Szenariogrundriss: K-Frage mit 3 Aussagen
    Angenommen eine K-Frage mit 1 Punkt und 3 Aussagen
    Wenn der Kandidat <richtig> Aussagen richtig, <falsch> falsch und <offen> nicht zuordnet
    Dann erhält er <Punkte> Punkte

    Beispiele:
      | richtig | falsch | offen | Punkte |
      | 3       | 0      | 0     | 1      |
      | 2       | 1      | 0     | 1/3    |
      | 1       | 2      | 0     | 0      |
      | 2       | 0      | 1     | 2/3    |

  @UC-01 @BR-43 @BR-46
  Szenariogrundriss: Bestehensgrenze 60 %
    Angenommen eine Prüfung mit 50 erreichbaren Punkten
    Wenn der Kandidat <erreicht> Punkte erreicht
    Dann lautet das Ergebnis <Ergebnis>

    Beispiele:
      | erreicht | Ergebnis        |
      | 30       | bestanden       |
      | 89/3     | nicht bestanden |
      | 50       | bestanden       |
      | 0        | nicht bestanden |

  @UC-01 @BR-40 @BR-41 @BR-42
  Regel: Invariante – jede Frage bringt zwischen 0 und ihrer Punktzahl
    Szenario: Zufällige Antworten bleiben im Wertebereich
      Angenommen 1000 zufällig erzeugte Fragen aller drei Typen mit 1 oder 2 Punkten
      Wenn für jede Frage eine zufällige Antwort bewertet wird
      Dann liegt jedes Ergebnis zwischen 0 und der Punktzahl der Frage
      Und jede vollständig korrekte Antwort erhält genau die Punktzahl der Frage

  @UC-01 @BR-43
  Regel: Invariante – das Ergebnis hängt nur vom Anteil ab
    Szenario: Skalierte Punktzahlen ändern "bestanden" nicht
      Angenommen eine bewertete Prüfung
      Wenn alle Punktzahlen der Fragen verdoppelt werden
      Dann bleibt der Prozentwert gleich
      Und das Ergebnis "bestanden" oder "nicht bestanden" bleibt gleich

== UC-02 Problem zu einer Frage melden

# language: de
Funktionalität: UC-02 Problem zu einer Frage melden

  Grundlage:
    Angenommen die Schwelle ist 3
    Und Frage "AG-01" hat die aktuelle Version "v1" im Status "Released" mit 0 Meldungen
    Und ein Kandidat hat eine Prüfung mit "AG-01" an Position 7

  @UC-02 @BR-51 @BR-52 @BR-54 @BR-58
  Szenario: MSS – Meldung zur Frage
    Wenn der Kandidat zu Position 7 eine Meldung der Kategorie "unclear" mit Text "Option C und D meinen dasselbe" abgibt
    Dann speichert das System die Meldung zu "AG-01" Version "v1"

  @UC-02 @BR-15
  Szenario: MSS – Meldung zu einer Antwortoption zählt für die Frage
    Wenn der Kandidat zu Position 7 und Option "C" eine Meldung der Kategorie "wrong" abgibt
    Dann speichert das System die Meldung mit Option "C"
    Und der Meldungszähler von "v1" ist 1

  @UC-02 @BR-53 @BR-56
  Szenario: Extension 2a – Kontaktdaten mit Einwilligung

  @UC-02 @BR-53
  Szenario: Extension 2a – Kontaktdaten ohne Einwilligung
    Wenn der Kandidat eine Meldung mit Name "Erika Muster" ohne Einwilligung abgibt
    Dann antwortet das System mit Status 422 und Code "INVALID_REPORT"
    Und das System hat nichts gespeichert

  @UC-02 @BR-51
  Szenario: Extension 3a – Kategorie fehlt
    Wenn der Kandidat eine Meldung ohne Kategorie abgibt
    Dann antwortet das System mit Status 422 und Code "INVALID_REPORT"
    Und der Meldungszähler von "v1" ist 0

  @UC-02 @BR-52
  Szenario: Extension 3a – Text zu lang

    Dann antwortet das System mit Status 422 und Code "INVALID_REPORT"

  @UC-02 @BR-54

    Dann speichert das System die Meldung

    Und der Meldungszähler von "v1" ist 1

  @UC-02 @BR-13 @BR-65
  Szenario: Extension 5b – Schwelle erreicht

  @UC-02 @BR-58
  Szenario: Extension 5c – Meldung zu einer veralteten Version
    Angenommen ein Import hat Version "v2" von "AG-01" angelegt
    Und "v2" ist Released
    Wenn der Kandidat zu Position 7 eine Meldung abgibt
    Dann zählt die Meldung für "v1"
    Und Meldungszähler und Status von "v2" bleiben unverändert

  @UC-02 @BR-50
  Szenario: Meldung nach der Abgabe
    Angenommen der Kandidat hat die Prüfung abgegeben
    Wenn er zu Position 7 eine Meldung abgibt
    Dann nimmt das System die Meldung an

  @UC-02 @BR-54
  Regel: Invariante – der Meldungszähler einer Version ist höchstens die Zahl der Prüfungen mit Meldungen zu ihr
    Szenario: Viele Meldungen aus wenigen Prüfungen
      Angenommen 3 Prüfungen enthalten "AG-01" in Version "v1"
      Und die Schwelle ist 100
      Wenn aus jeder Prüfung 5 Meldungen zu "AG-01" eingehen
      Dann ist der Meldungszähler von "v1" 3
